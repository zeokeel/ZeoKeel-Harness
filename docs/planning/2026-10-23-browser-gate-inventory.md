# 内置浏览器「拦截」全量清单（决策用）

- 日期：2026-10-23
- 范围：`packages/host/browser`（`@zeokeel/dsh-browser`）里所有**会挡住动作、限制能力、改写数据出口或限流**的机制，共 **52 项**（A–H 八组）。
- 用法：每项一行判据（证据 `file:line` / 现状 / 关掉后发生的具体事 / 风险 / 我的建议 / 改动量）。**你只需要在 §9 的三张清单里勾**：「关」「放宽」「留」。
- 口径：
  - **拦截** = 请求被拒绝或被迫等待；**能力边界** = 根本不提供该能力；**脱敏** = 放行但改写内容。三者常被混称「拦截」，这里分开列，因为关掉的代价完全不同。
  - 「改动量」：S ≈ 1–2 天，M ≈ 3–5 天，L ≈ 1–2 周+（含测试与客户端面）。
  - 与「本地信任模式」相关：**编程模式（`browser_run`）不会自动绕过下列任何一项**——脚本里的每次调用仍走同一套 runtime 与 gate。所以「先做 browser_run」和「逐条拆 gate」是两件独立的事。

## 10. 与 `browser_run`（Q1 选定的 C 方案）的关系

**结论：先做 `browser_run` 也不会自动获得「无拦截」——脚本里每次调用仍走同一套 runtime。** 两项工作的依赖关系：

| `browser_run` 需要什么 | 现状 | 需要你决定 |
| --- | --- | --- |
| 脚本 API 面（约 20–24 个方法：`open/navigate/snapshot/click/type/select/press/scroll/wait/screenshot/text/eval/tabs/close/bookmarks/downloads…`） | 全部已有 runtime 方法，只需一层薄封装 + TS 类型 | 是否暴露 `eval`（与 F1 一致） |
| 执行载体 | 可复用 `ctx.ptcRuntime`（独立 Node 进程 + 沙箱 + 预算），或自建 `vm` 沙箱（更轻，但要自己控超时/输出） | 复用 PTC（推荐，改动小、能力与上游一致） |
| 脚本级预算 | PTC 默认 120s / 上限 600s；单工具 30s | 用 120s 还是给浏览器单独配 300s |
| 脚本内遇到用户闸/凭据窗口/导航策略时 | 现有 gate 逐个生效；模型会在脚本里收到错误对象 | 是否在脚本里改为「抛错终止脚本」而不是逐步重试 |
| 输出 | 脚本 `console.log` + 返回值；长输出会占上下文 | 是否沿用 `spill`（上游大输出落盘）而不是截断 |

**建议的落地顺序**：① 先做 `browser_run`（不改任何 gate，纯新增能力，可单独验收）；② 再按你在 §9 勾的结果逐条改 gate；③ 最后把「本地信任模式」做成一个设置项（默认开），把 §9.1/§9.2 的开关收进去，§9.3 不进这个开关。
