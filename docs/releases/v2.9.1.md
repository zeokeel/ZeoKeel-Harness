## 一、为什么会有 v2.9.1

- **现象**：`v2.9.0` 的发布流水线在"官方 Windows 安装器验收"这一步失败，
  `release` job 被跳过 ⇒ GitHub Release 与更新服务器**都没有 v2.9.0 的产物**。
- **根因**：该验收脚本在"静默卸载"之后**立即**检查安装目录是否消失；而 Windows 卸载器
  的自删除/清理可能在进程退出之后才完成 ⇒ 检查过早，把一次正常的卸载判成"残留"。
  这是**验收脚本**的缺陷，不是安装器或产品代码的缺陷。
- **修法**：验收改为**轮询等待**（目录与注册表项，上限 60 秒）再判定；其余断言不变。
  该修正已并入本次发布，并在 Windows CI 上重新通过。
- **不会影响任何人**：`v2.9.0` 没有产出可下载产物，也没有写入更新服务器；你不需要做任何清理。

## 二、与 v2.9.0 相同的客户侧变化（摘要）

- **Windows 一键安装、仅当前用户、静默升级**：双击即装、无向导、无 UAC；
  应用内更新用静默参数原地升级。安装目录为 `%LOCALAPPDATA%\Programs\dsh-plugin-desktop`。
- **旧版迁移**：改名前发布的 2.8.x（含全局安装）不会被静默覆盖；
  交互安装会提示、静默更新以退出码 2 结束并在应用内弹原生提示。
  **请先在「设置 → 应用」卸载旧版本**；旧数据根与新版不同名，历史会话/设置不会自动迁移。
- **启动失败自救**：致命启动对话框提供"跳过第三方插件"与"备份补丁并重启"；
  安全模式一次性生效、成功后自动恢复；重复失败会自动升级为同时备份补丁，不会进入死循环。
- **合规与门禁**：一键安装器不再显示许可页，`LICENSE` 与第三方声明随安装包分发；
  CI 对安装器做载荷断言与真实静默安装/重装/卸载验收（带硬超时）。

## 已知限制

- **Windows 安装器仍未代码签名**：首次双击可能出现"未知发布者"/SmartScreen；
  静默升级被拦截时表现为"更新看起来没发生"，请重新检查更新或手动安装。
- **旧版（改名前）安装的数据根不迁移**：旧全局安装必须先手动卸载；旧会话/设置需自行备份迁移。
- **Windows 每次更新下载完整安装包**（无差分更新）；**Linux 仍为 AppImage**，新版本需手动替换。
- 同一台机器的不同渠道共用同一个 Windows 安装目录名，渠道数据靠各自的数据根分离。

## 升级与回滚

- **服务端**：取 `zeokeel-server-2.9.1-amd64.zip` → `docker load` → 按 `docs/deploy/AI-DEPLOY.md`
  升级（**升级前必须备份**整个数据根，不要使用 `latest`，不要 `down -v`）。
- **客户端**：随服务端镜像/更新入口分发；服务端与客户端保持同版本。
- **迁移清单（机器可读锚点，供 `scripts/check-release-notes-migrations.mjs` 与 `git diff` 对拍）**：无
- **回滚**：口径唯一真源是 `docs/deploy/AI-DEPLOY.md` §7。本版相对 `v2.9.0` 无数据库迁移；
  回退到 `v2.8.3-beta.5` 或更早版本同样无数据库迁移，换回对应镜像与客户端包即可。
  Windows 若要从本版退到向导式安装器的旧版本，建议先卸载本版再安装旧版包。

## 附件与校验

- `zeokeel-server-2.9.1-amd64.zip`：服务端镜像压缩包（`docker load` 后使用），内含该渠道的三平台客户端安装包；
- `SHA256SUMS`：先 `sha256sum -c SHA256SUMS` 校验，再解压。
- 客户端安装包在镜像内（`/opt/zeokeel/client/`），员工也可从自己服务器的更新页面下载。
  品牌渠道的镜像与客户端只在该渠道自己的更新目录里，不随公开 Release 发布。
